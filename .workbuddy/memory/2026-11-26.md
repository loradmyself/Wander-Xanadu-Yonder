## 覆盖层方案失败 → 帧率真正根因确定并修复（禁用 EPIC draw unit）
- 用户复测：覆盖层淡入后 render 仍 534~589ms，一点没降，**方案判失败**。
- 决定性推理：`cpu_get_usage=0%` + `LVGL 线程 99% 忙` = 阻塞等信号量，不是计算。
  纯 SW 逐像素绘制必吃满 CPU → 推翻「LABEL 走 SW 画字慢」/「重绘整棵树」/「离屏合成」三个中间判断。
- 真根因：`CONFIG_LV_OS_NONE 1`（LV_USE_OS=0），EPIC 是同步 draw unit；
  `execute_drawing()` 每个 task 开头(397)+结尾(444) 各调 `drv_epic_wait_done()`
  = `drv_gpu_check_done(500)`，GPU 完成信号不到位时 `wait_gpu_done()` 等满 500ms
  再 gpu_reset 重试 → 每次整屏重绘固定 ~540ms。EPIC 占用 <1% 说明 GPU 没在加速。
- 修复（SDK 单点补丁）：`lv_drivers_v9/sifli/lv_draw_epic.c` 加
  `#define WXY_DISABLE_EPIC_DRAW_UNIT 1`，`lv_draw_epic_init()` 不再注册 unit，全走 SW。
  安全确认：`lv_draw_sw_init()` 在 lv_init.c:239 先注册；`drv_gpu_open()` 在 drv_lcd.c
  另有 3 处，刷屏走 drv_lcd_fb_write_send 不依赖 EPIC unit。
- 统一补丁 `docs/patches/sifli-lvgl9-sw-only.patch`（取代旧的 label-only 补丁）。
- 编译验证：main.bin **703,368 B**；`lv_draw_epic_init` 2 字节 bx lr，
  lv_draw_epic_fill/border/label/execute_drawing 全被 GC（符号数 0）。待用户复测。
- 教训：瓶颈定位看 CPU/线程占用是否匹配。cpu 0% + 线程 99% 忙 = 等，不是算；
  光看 render/flush 分解也会误判（render 大不等于 CPU 在算）。

## framebuffer 双缓冲修复（19:35~20:08，上板前）

用户在 project/proj.conf 开了 LCD_FB_USING_TWO_UNCOMPRESSED + LV_FB_TWO_SCREEN_SIZE，编译报
CMPR_DATA_TYPE unknown。根因两层：
1. **板级 proj.conf 覆盖顶层**（Wander-Xanadu-Yonder_hcpu/proj.conf 后加载），用户顶层写的
   TWO_UNCOMPRESSED 被板级 ONE_COMPRESSED 压掉；顶层 LV_FB_TWO_SCREEN_SIZE 也被压成 TWO_NOT_SCREEN_SIZE。
2. **LB57 无 EXTDMA 压缩外设**：Kconfig `BSP_USING_EXT_DMA` default y 只列了 55/56/58/52；
   `HAL_EXTDMA_MODULE_ENABLED` 还要 `#ifdef EXTDMA_BASE` 才定义 → sifli_cmpr.h 不进编译单元 →
   CMPR_DATA_TYPE/CMPR_*_COMPRESSED_BYTES 全部未定义。COMPRESSED 路径在 57 上永远编不过。

最终落地组合（板级 proj.conf）：
- `CONFIG_LCD_FB_USING_TWO_UNCOMPRESSED=y`：PSRAM 双全屏 fb（map 实测 0x60200000 起 0x258000=2.4MB，
  两块 1.2MB），防撕裂，flush last 时 switch_draw_buf 轮换。
- `CONFIG_LV_FB_ONE_NOT_SCREEN_SIZE=y` + `LV_FB_LINE_NUM=100`：LVGL 保持 L1 单块 100 行（0x32000=200KB）。
  期间试过 LV_FB_TWO_NOT_SCREEN_SIZE（LVGL 也双块）→ L1 RAM overflow 51,888 B，必爆。
- 顶层 proj.conf 删掉这两行（会被板级覆盖，写了不生效），留注释说明优先级。

产物：main.bin **713,992 B**。LVGL 私有堆 [60000000,60200000) 与 fb [60200000,60458000) 不冲突。

教训：proj.conf 有两层，改动要落在板级那份；choice 类选项被覆盖后顶层怎么写都没用。

## M55 Helium 加速启用（20:30~21:00）

上板数据 render ~530ms + CPU 99%：真在算，纯 C 混合太慢。三个发现：
1. **HCPU 被 SDK 按 M33 编译**：building.py GetMtune/GetMarch 对 LB57X 给 cortex-m33/
